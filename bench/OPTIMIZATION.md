# 第一轮优化结果

测量日期：2026-11-06，Asia/Shanghai。

本轮修复数组契约校验错误，优化提交后的通知和重复刷新。普通更新的传播 P95 明显下降；当前仍发送完整快照，传输量仍高于 Meteor 增量协议。

## 实现变化

- 数组声明的 `maxItems` 超过 100 时立即拒绝；省略时仍默认 100，允许 0 和 100 两个边界。
- 业务数据、幂等结果和 Oban 通知任务仍在同一事务内提交。最外层事务成功后立即发送失效通知，省去等待任务调度的延迟；持久化任务保留为失败兜底。
- 调用方已有事务时，不提前发送即时通知，由提交后可见的 Oban 任务负责通知，避免回滚数据被提前广播。幂等重放不产生新通知。
- 即时与持久化通知携带同一个任务 ID。channel 保存最近 64 个 ID，跳过重复通知带来的查询；乱序的新通知正常处理，淘汰后的旧 ID 重放只会触发一次安全查询。
- 每次实际查询仍重新鉴权并校验结果大小。自动刷新通过 SHA-256 指纹跳过内容不变的快照；显式 `refresh` 保持原来的响应行为和 ACK 规则。
- 大小校验、内容指纹和快照 Telemetry 复用同一次 JSON 预编码。channel 保存指纹，不缓存上一份完整结果。协议仍为 v1，现有 TypeScript SDK 可以直接使用。

## 测量条件

Apple M3 Pro，12 个逻辑 CPU，36 GiB 内存；应用、数据库和负载发生器在同一台机器，没有固定资源限额。Fyrlet 使用 Elixir 1.20.5、OTP 29、Phoenix 1.8.16、PostgreSQL 17.11；Meteor 使用 3.5.4、Node 24.22.1、MongoDB 7.0.16，并配置 oplog。

优化前后均为：每用户 50 条记录、正文 128 字节、30 次测量写入、5 次预热写入、重复 3 轮，最多 2 个用户、每用户 2 个观察端。慢客户端每条消息延迟 30 ms。`smoke` 配置中的连接数和空闲时长仍很小，不代表容量或长期稳定性测试。

优化前已经包含数组校验修复，基线来自修改通知链路前保存的报告。优化后 Fyrlet 与 Meteor 使用同一份代码指纹。每轮独立计算 P95，表格展示三个 P95 的最小值至最大值，不对分位数求平均。

## 结果

传播时间从写入请求开始，到其他客户端应用对应服务端记录结束，单位 ms。

| 场景 | Fyrlet 优化前 P95 | Fyrlet 优化后 P95 | Meteor P95 |
| --- | ---: | ---: | ---: |
| 同用户多设备 | 13.31–14.06 | 3.36–5.81 | 2.14–3.40 |
| 不同用户并行 | 12.59–12.90 | 3.23–4.51 | 1.60–2.13 |
| 连续突发写入 | 5.51–8.52 | 3.21–4.04 | 2.33–5.41 |
| 慢客户端 | 88.02–114.65 | 62.46–63.64 | 663.06–680.00 |

前两种场景的中间状态交付覆盖率均为 100%，可以直接比较本轮传播延迟。突发写入的 Fyrlet 覆盖率由 40–50% 提高到 100%，Meteor 为 100%。慢客户端的 Fyrlet 覆盖率由 20–28.3% 提高到 55%，Meteor 为 100%；这里的低延迟也受到合并中间状态的影响，不能宣布 Fyrlet 胜出。所有场景最终视图均正确。

断线恢复的 `recoveryMs.p95`：Fyrlet 优化前 6.61–6.82 ms，优化后 6.59–7.46 ms；Meteor 16.04–18.77 ms。恢复指标从统一重连起点计算，与上表传播指标不同；本轮没有显示 Fyrlet 重连速度的明确提升。

多设备场景每轮接收的应用载荷约为：Fyrlet 优化前后均 1,003 KB，Meteor 31 KB。这里统计预热后的 HTTP 正文和 WebSocket 应用载荷，不含帧、头部和 TLS。正常更新仍需发送完整视图，无变化快照去重没有减少此场景的传输量。全量快照相对于增量推送的差距随视图大小增加而扩大，后续应优先处理这一点。

优化前 Fyrlet 18 次场景执行通过；最终 Fyrlet、Meteor 共 36 次执行通过，资源采样无报错。结果支持本轮实现的低负载延迟改进，不支持 Phoenix 相对于 Node 的通用排名，也不支持最大吞吐量推断。
