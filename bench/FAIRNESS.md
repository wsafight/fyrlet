# Meteor / Fyrlet 同等条件对照规范

自 2026-11-06 起，后续用于性能结论的对照遵循此规范。现有本机运行只作为观察结果；完成相同负载并不代表已经落实相同资源和保障。

## 结论门槛

正式对照必须保存操作系统实际生效的资源限制、部署配置、完整负载、业务保障清单及原始结果。任一条件未完成，只报告各自测量值和缺失条件，不发布“同等条件更快”的结论。

当前 `local.mjs` / `capacity.mjs` 不落实 CPU 或内存硬限制，生成器和数据库也与应用共用主机。`report.mjs` 将跨实现结果标记为 `observational-only`，核对完整负载、源码指纹和主机信息，并列出资源与保障差异。相同的 `+S`、容器声明参数或平均 CPU 占用不作为资源限制已生效的证据。

`local.mjs` / `capacity.mjs` 仍是上述无限额的本机启动器。单核组已另用 Colima 虚拟机中的 Docker 容器完成一次限额对照（结果与边界见 [性能对比](../docs/PERFORMANCE.md)），运行脚本尚未整理进仓库。

## 资源与部署

分别建立两个对照组，组内条件固定，不把不同组的数字混在一起：

| 对照组 | 应用总预算 | 目的 |
| --- | --- | --- |
| 单核 | 双方各 1 vCPU、1 GiB | 比较相同单核预算下的延迟、吞吐与资源开销 |
| 多核 | 双方各 4 vCPU、4 GiB | 比较相同总预算下各自正常扩展方式 |

这些是下一轮计划的预算，不是历史运行的限制。可以根据空载实际需求统一调整双方预算，但必须在正式运行前固定并写入配置。

- 使用同代硬件及同一操作系统，在隔离环境限制整个应用进程组的 CPU 与内存，保存实际限制及节流、OOM 计数。BEAM 的 4 个调度器与一个 Node 进程不能据此认定为同等 CPU 预算。
- 多核组允许 Meteor 使用多个服务 Node 进程、Fyrlet 使用 BEAM 调度器；应用所需的代理、负载均衡及辅助服务都要计入同一总预算。记录实例数、连接分配、粘性会话及观察者是否跨进程重复。
- 两边均使用正式构建产物：Fyrlet release、Meteor production bundle。构建、CLI、文件监视与首次依赖解析全部在计时外；访问路径使用相同代理配置或均直接连接。
- 数据库单独分配相同的 CPU、内存和存储预算，使用各自正常的 PostgreSQL / MongoDB 路径。对齐事务持久性、刷盘、写确认、索引与连接池策略；不强制不同数据库拥有相同的内部结构。
- 生成器放在独立资源域，优先独立主机；记录网络、TLS、压缩、机器温度和限频情况。生成器掉拍时，该点不能证明服务端容量上限。
- 资源报告分别列应用进程组、服务进程、数据库和生成器。服务进程属于应用进程组，不能相加。多进程共享内存用合适的进程组指标或 PSS 说明；不用 PostgreSQL 各进程 RSS 求和直接给 MongoDB 内存排名。

## 相同业务与交付条件

内部实现可以不同，但对外工作量和成功条件必须一致：

| 条件 | 要求 |
| --- | --- |
| 数据 | 相同用户、每用户记录量、字段、有效载荷、索引覆盖与初始化历史 |
| 连接 | 相同观察者数与写入连接数，显式记录总连接数 |
| 会话 | 分别测同会话多设备、独立登录多设备；允许各自正常的安全查询复用 |
| 写入 | 相同全局速率、持续时间、并发、版本冲突策略及事务幂等要求 |
| 订阅 | 相同窗口、排序、增量字段及最终完整记录校验 |
| 中间状态 | 逐次交付与允许合并的场景分别比较；延迟必须与实际覆盖率一起报告 |
| 恢复 | 相同断线时长、离线变更、恢复起点及最终收敛条件 |
| 安全 | 明确到期、撤销、每次变更重新鉴权和撤销/写入竞态的要求 |
| 确认 | 区分写入提交、服务端回复、订阅应用与 ACK；不同完成条件的 writeMs 不直接排名 |

当前 Meteor 参考实现对 Method / publication 入会检查会话、用定时器结束到期订阅；它没有 Fyrlet 的逐次刷新重新鉴权及撤销/写入串行化。正式同保障对照须先补齐并通过相同的业务验收。也可另设双方都实现的公共功能测试，但不得把它描述成完整产品保障相等。

## 执行与验收

1. 固定双方源码、运行时、SDK、数据库版本和资源配置。构建、初始化、预热全部在计时窗口外；历史的 `warmup=0` 结果单独标记。
2. 冷启动、充分预热、长时间运行分开测试。同一套脚本传入相同用户、设备、行数、字节、速率、并发、超时、预热与持续时间。
3. 使用相同预热和缓存策略；每个正式独立重复重新初始化应用与数据，记录清理结果。当前本地启动器的 repeats 复用服务进程，不能把它当成冷启动独立重复。
4. 至少 3 个独立重复，交替执行顺序，例如 Fyrlet / Meteor / Meteor / Fyrlet，减少温度与缓存顺序偏差；不同时运行两边的计时负载、构建或测试。
5. 记录每轮延迟、成功写入、offered / dispatched、生成器/并发/用户忙导致的跳过、错误、覆盖率、最终数据、连接数、CPU、内存及限额节流，不平均多轮的 P95。
6. 长时间稳定性另设持续负载和断连恢复，不从 20–60 秒或历史 3 分钟测试推断长期无泄漏；以全部重复都通过的负载点报告已验证范围，不插值成最大容量。
7. `local.mjs` 在每个目标计时前后校验源码，`capacity.mjs` 在各负载点前后校验整套源码；变化会中止该套对照。诊断采样和 profiler 单独运行，不混入正式性能数字。

## 当前状态

已完成：共享场景、严格最终校验、会话模式拆分、资源分项、直接访问 Meteor app-port、超时记录、源码变化中止、报告条件核对；**单核组**（应用各 1 vCPU / 1 GiB，数据库各 2 vCPU / 2 GiB，生成器独立 cpuset，容器 cgroup 强制限额，交替顺序）的一次对照，每个负载点 2 次重复。

未完成：多核组（4 vCPU / 4 GiB）与 Meteor 多进程总预算方案、同保障验收（Meteor 没有逐次重新鉴权，写确认强度也未对齐）、每点至少 3 个独立重复、冷启动与长时间稳定性验证、可复用的限额部署脚本。因此现有数据只能支持单核、单机虚拟机、短时间负载下的观察，不能外推到其他预算或保障条件。
