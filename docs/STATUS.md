# Implementation status and acceptance matrix

This document records the implementation status of each capability and how acceptance scenarios map to automated verification. The verification environment, raw evidence and reproduction commands are in [ACCEPTANCE.md](ACCEPTANCE.md); test counts are whatever the output of `bash scripts/test_all.sh` and `npm --prefix sdks/typescript test` reports.

Meaning of the statuses: **Implemented** (has automated tests), **Partial**, **Not implemented**. The acceptance matrix is a target list; it does not mean every production scenario has been verified. Physical mobile devices, multi-host production environments, 24-hour stability, real email delivery and Hex / npm publishing are not yet verified.

Two points to make explicit:

1. Capability packages fall into standalone plugins (Webhooks, Ops) and standalone adapters (HTTP, Email) by nature, all in `packages/`. The anonymous entry, ingestion, the HTTP executor and the append channel change core identity or protocol, so they remain optional core features. Plugin runtime code connects through the public `Fyrlet.Transaction`, `Fyrlet.HTTP`, `Fyrlet.Diagnostics` and the Run/Effect entry points, and does not reference the core Engine, the Signal schema or internal Web response modules; application tests use `Fyrlet.Testing`. The complete public list is in [INSTALL.md](INSTALL.md), and the classification is in [PLUGINS.md](PLUGINS.md).
2. Concurrency-related assertions (concurrent creation, concurrent claiming, signal versus timeout, cancellation versus completion, project concurrency cap) are verified in `runs/concurrency_test` **without the sandbox, with real commits**; the other tests run in the Ecto sandbox, so row-lock contention can only be covered by this group.

## Base acceptance (A01–A18)

| ID | Scenario | Pass criterion |
| --- | --- | --- |
| A01 | Start from a clean environment | Dependency installation, database initialization, development account creation and service startup are completed as documented |
| A02 | Input validation | A wrong type or field returns a stable error code, and no business write happens in the database |
| A03 | Identity and data isolation | User A cannot read, modify, subscribe to or, through Scope, obtain user B's records |
| A04 | Successful write | A successful response corresponds to committed data, and another connection eventually receives a snapshot containing the record |
| A05 | Concurrent duplicate requests | The same idempotency key with the same input produces only one business record and returns a consistent result |
| A06 | Conflicting requests | The same idempotency key with different input, and an expired record version, both return an explicit conflict |
| A07 | Transaction rollback | A business failure keeps no successful idempotency result and triggers no corresponding data notification |
| A08 | Interruption after commit | If the process is interrupted after the commit succeeds but before the notification is published, the affected subscriptions can still be refreshed after recovery |
| A09 | Initial query race | Establishing a subscription and writing run concurrently; the final data contains the latest commit without the user reopening the application |
| A10 | Change during a query | If a write happens again before a refresh completes, the old result cannot permanently overwrite the new one |
| A11 | Duplicate and out-of-order handling | Duplicate invalidation notifications do not write twice; verify that the client ignores old generations and old sequence numbers |
| A12 | Disconnection and restart | After a disconnection, writes continue; after reconnecting or restarting the service, the correct current snapshot can be obtained |
| A13 | Missed notifications | Notifications are dropped on purpose; under healthy conditions the periodic check repairs the data within the agreed window |
| A14 | Permission revocation | After revocation, operations and snapshot delivery are rejected, and the subscription is closed within the agreed re-check window |
| A15 | Query scope change | When additions, archiving or deletions change the recent list, the next snapshot has the correct order and members |
| A16 | Resource reclamation | After a subscription is cancelled or a connection is dropped, the related listeners and timers are released |
| A17 | Slow client | Resources are bounded, snapshots do not pile up without limit; after a disconnection the current state can be read again |
| A18 | Protocol and baseline | The contract can be exported, errors are documented, and performance results come with a reproducible environment and scripts |

R05, R06, R08, R23 and R24 must be verified through **fault injection**. Injection points: after claim and before execution (`:after_claim`), before the result is committed (`:before_commit`), after the result is committed and before notification (`:after_commit`), between the advancement decision and the wake-up (`:before_wake_insert`), after an Effect is claimed (`:effect_claimed`) and after the external call returns and before settlement (`:effect_before_settle`), cancellation concurrent with completion, and a recovery scan concurrent with a late result. An integration test that covers only the happy path does not count as passing.
