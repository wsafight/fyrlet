# Append subscriptions (Stream)

Optional capability `append`. It is for **immutable appended records**: message events, logs, Run events. The subscription data is the window of "the latest N items at most"; new records are appended in batches, and old records are evicted by the window. For the wire format see [PROTOCOL.md](PROTOCOL.md#append-subscriptions-capability-append), and for how to write it on the application side see [SERVER.md](SERVER.md#append-subscriptions-and-fyrletfeaturesstream).

## Scope

- Only **appends** are supported. Delta events do not contain `update` / `delete` / arbitrary JSON Patch.
- Queries that do not fit append semantics remain ordinary snapshot subscriptions. When a published record needs to be corrected or deleted, the server must reset the stream (see below); clients must not keep treating old records as immutable facts.
- The snapshot is the authoritative state of the current window, not the complete history. An application that needs a complete log provides its own history pagination, cursor validity period, retention period and a "history truncated" marker.
- This is a different thing from the field-level delta of ordinary subscriptions (`delivery: "delta-v1"`, for field changes of existing records), and the two do not affect each other.

## Contract and definition

A subscription declares `mode: "append"`, `max_items` (1–500) and `capability: "append"` in the contract; the definition implements `stream/3`, which returns the stream name of `Fyrlet.Features.Stream` (called after `authorize/3`). Validation is done when the registry loads, and if any item is missing the application fails to start. The server must enable `capabilities: %{"append" => 1}`.

## Streams and positions

A stream is stored in two tables: `fyrlet_streams` (one row per stream: `head`, `epoch`, `trimmed_before`) and `fyrlet_stream_entries`.

- `Fyrlet.Features.Stream.append/3` **must be called inside a transaction**. It takes a number on the stream row and holds the lock until commit; appenders to the same stream commit in the order they took numbers, and a rollback returns the position.
- When a reader sees `head = H`, it is guaranteed that all entries with a position not greater than `H` have been committed. A position is a persistent position within the stream; it is not the auto-increment ID of the source record, a timestamp, or the arrival order of PubSub notifications, and **they cannot be converted into one another**.
- A cursor is an opaque string generated by the server. The client only compares for equality; it does not parse it and does not use gaps to decide whether messages were lost.

## Joining and acknowledgement

- The initial snapshot, window metadata and position come from a consistent data view. The server **sets up the change listener first and then reads** the snapshot and position, and fills in the records after that position, so that no gap appears between the snapshot and the deltas.
- The server must guarantee that each batch covers **all** visible appended records between `base_cursor` and `cursor`; it cannot rely on PubSub notifications alone to assemble history.
- The client applies the items of a whole batch only when `generation` is valid, `seq` is exactly the current value plus one, and `base_cursor` equals the local cursor; a duplicate packet is not applied twice; if not contiguous, it stops merging and sends `refresh`.
- `ack` carries `{g, s, c}` (generation, cumulative seq, corresponding cursor); all three must agree with the server's record, otherwise it is ignored. `seq` is the send sequence number within the subscription, not a database position.
- Each subscription has at most one unacknowledged snapshot, and no delta is sent before it is acknowledged. Subsequent deltas can be acknowledged cumulatively, but the unacknowledged window is at most 200 batches or 256 KiB by default (`config :fyrlet, :streams, window_batches:, window_bytes:`); when either is exceeded, deltas stop and a `snapshot` with the same generation and a higher `seq` is sent to reset the view and position. An old acknowledgement cannot overwrite a newer baseline.
- An acknowledgement timeout (`snapshot_ack_timeout`) closes the subscription, so memory does not pile up without bound for a slow client; the size of a single packet, send throttling and the total queue per connection are likewise bounded.

## Window and history

- After the client appends, the oldest items are evicted according to `max_items`, so a bounded snapshot does not become an unbounded local list.
- When a cursor cannot be resumed (`epoch` changed, the position is beyond `head`, or it has been trimmed by `Fyrlet.Features.Stream.prune/2`), it always falls back to a snapshot. The SDK does not claim to have filled in the history from the offline period.
- Correcting or deleting a published entry must call `Fyrlet.Features.Stream.reset/2` (a new `epoch`), which invalidates all old cursors.
- Retention: the scheduled job of `mix fyrlet.prune` trims each stream according to `retention_items` (default 10 000).

## Authorization and shared reads

- All members see the **same** entries; there is no per-member trimming. Authorization applies to the subscription as a whole (`authorize/3`), and the session and authorization are re-checked **before every send**.
- Within the same node, `Stream.Reader` uses a bounded cache to merge reads with the same project / stream / cursor / options, and falls back to independent reads when the cache is unavailable. The cache holds no authorization decision, and each connection still re-checks independently.
- Each node uses its own cache; no global cross-node cache is implemented; invalidation propagates across nodes through PubSub. For data that must be filtered per member, use a private snapshot subscription.

## Telemetry

- `fyrlet.delta.snapshot_fallback`: fallback to a snapshot, with `reason` being `gap`, `overflow` or `refresh`.
- `fyrlet.subscription.append`: bytes and item count of each batch.
